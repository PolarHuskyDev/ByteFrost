# Tokenizer

The ByteFrost tokenizer (also called the **lexer**) is the first stage of the compiler pipeline. It reads raw source code text (`.bf` files) character by character and emits a flat stream of **tokens** — the smallest meaningful units of the language.

Downstream stages (parser, semantic analyzer) never touch raw text; they operate entirely on the token stream produced here.

---

## Token Structure

Every token carries four pieces of information:

| Field    | Type     | Description                                              |
|----------|----------|----------------------------------------------------------|
| `type`   | `TokenType` | Category of the token (see below)                    |
| `value`  | `string` | Exact source text that produced this token               |
| `line`   | `int`    | 1-based line number in the source file                   |
| `column` | `int`    | 1-based column number of the token's first character     |

Location information (`line`, `column`) is preserved throughout the pipeline so that error messages can point precisely to the offending source position.

---

## Token Types

```
TokenType
├── Identifier   — user-defined names (variables, functions, types, …)
├── Keyword      — reserved words with special meaning
├── Number       — integer or floating-point numeric literals
├── String       — string and character literals (including interpolated strings)
├── Operator     — punctuation, symbols, and multi-character operators
├── EndOfFile    — sentinel emitted once the entire input is consumed
└── Unknown      — unrecognized character sequence (triggers a lexer error)
```

---

## Token Categories in Detail

### Identifiers

Any sequence starting with a letter (`A–Z`, `a–z`) or underscore (`_`), followed by zero or more letters, digits (`0–9`), or underscores.

```
letter    = "A".."Z" | "a".."z" ;
identifier = ( letter | "_" ) { letter | digit | "_" } ;
```

**Examples**

| Source text    | Token type   | Value          |
|----------------|--------------|----------------|
| `myVariable`   | `Identifier` | `"myVariable"` |
| `_count`       | `Identifier` | `"_count"`     |
| `Point3D`      | `Identifier` | `"Point3D"`    |
| `__reserved`   | `Identifier` | `"__reserved"` |

> A name that matches a reserved keyword is classified as `Keyword`, not `Identifier`.

---

### Keywords

Reserved words that cannot be used as identifiers. The tokenizer recognizes them by checking whether an identifier-shaped token matches the keyword table.

| Category         | Keywords                                                                            |
|------------------|-------------------------------------------------------------------------------------|
| Types            | `int` `float` `bool` `char` `string` `void` `array` `map`                           |
| Declarations     | `struct` `enum` `import` `from` `export` `as` `interface` `implements`, `implement` |
| Control flow     | `if` `elseif` `else` `while` `for` `in` `match` `return` `break` `continue`         |
| Boolean literals | `true` `false`                                                                      |
| Null             | `null`                                                                              |
| Logical ops      | `and` `or` `not` `xor`                                                              |
| Object           | `this`                                                                              |
| Async / await    | `async` `await`                                                                     |
| Nullability      | `option`                                                                     |

**Examples**

| Source text | Token type | Value       |
|-------------|------------|-------------|
| `if`        | `Keyword`  | `"if"`      |
| `elseif`    | `Keyword`  | `"elseif"`  |
| `return`    | `Keyword`  | `"return"`  |
| `struct`    | `Keyword`  | `"struct"`  |
| `and`       | `Keyword`  | `"and"`     |

> **Note:** `&&`, `||`, `!`, and `^^` are **not** valid in ByteFrost. Only the keyword forms (`and`, `or`, `not`, `xor`) are accepted. The tokenizer will emit `Unknown` for those symbol sequences.

---

### Number Literals

The tokenizer supports three integer bases and two decimal float formats.

```ebnf
integer_literal =
      digit { digit }           (* decimal   e.g.  255    *)
    | "0x" hex_digit { hex_digit }  (* hex  e.g.  0xFF    *)
    | "0b" bin_digit { bin_digit }  (* binary   e.g.  0b1010 *) ;

float_literal =
      digit { digit } "." digit { digit }   (* e.g.  3.14   *)
    | "." digit { digit }                   (* e.g.  .5     *)
    | digit { digit } "." ;                 (* e.g.  2.     *)
```

**Examples**

| Source text | Token type | Value          |
|-------------|------------|----------------|
| `42`        | `Int`      | `"42"`         |
| `0xFF`      | `Int`      | `"0xFF"`       |
| `0b1101`    | `Int`      | `"0b1101"`     |
| `3.14`      | `Float`    | `"3.14"`       |
| `.75`       | `Float`    | `".75"`        |
| `1e12`      | `Float`    | `"1e12"`       |
| `.3e4`      | `Float`    | `".3e4"`       |
| `1.2e-3`    | `Float`    | `"1.2e-3"`     |
| `.6e-3`     | `Float`    | `".6e-3"`      |
| `1_000`     | `Int`      | `"1_0000"`     |
| `12_000`    | `Int`      | `"12_0000"`    |
| `123_000`   | `Int`      | `"123_0000"`   |
| `1_234_000` | `Int`      | `"1_234_0000"` |

---

### String & Character Literals

All string forms are delimited by double quotes `"…"`. Character literals use single quotes `'…'`.

**Plain string**
```
"Hello, world!"
```

**Interpolated string** — any expression inside `{ }` is evaluated at runtime and spliced in:
```
"Welcome, {username}! You have {inbox.count} messages."
```

> The tokenizer emits the entire string literal (delimiters included) as a single `String` token and records the raw value. Interpolation expansion is handled by the parser.

**Character literal**
```
'A'   '\n'   '\\'
```

**Examples**

| Source text             | Token type | Value                     |
|-------------------------|------------|---------------------------|
| `"hello"`               | `String`   | `"\"hello\""`             |
| `"line {n}"`            | `String`   | `"\"line {n}\""`          |
| `'Z'`                   | `String`   | `"'Z'"`                   |

---

### Operators & Punctuation

Single-character symbols and multi-character compound operators are all classified as `Operator`.

| Category              | Tokens                                              |
|-----------------------|-----------------------------------------------------|
| Arithmetic            | `+` `-` `*` `/` `%`                                 |
| Compound assignment   | `+=` `-=` `*=` `/=` `%=`                            |
| Comparison            | `==` `!=` `<` `>` `<=` `>=`                         |
| Bitwise               | `&` `\|` `^` `~` `<<` `>>`                          |
| Logical               | `and` `or` `not` `xor`                              |
| Assignment            | `=`                                                 |
| Unary increment       | `++` `--`                                           |
| Delimiters            | `(` `)` `{` `}` `[` `]`                             |
| Punctuation           | `;` `:` `,` `.`                                     |
| Nullable / type       | `T?`                                                |
| Null-safe access      | `<obj>?.<field> : <fallback>`                       |
| Arrow (match)         | `=>`                                                |
| Ternary               | `<boolean expr>? <true expr> : <false expr>`        |

---

### End of File

A single `EndOfFile` token is appended after all source characters have been consumed. The parser treats this as a safe termination sentinel instead of requiring null checks.

---

## Whitespace & Comments

Whitespace (spaces, tabs, newlines) and comments are **consumed and discarded** by the tokenizer — they produce no tokens but do advance the line/column counters.

```
// This is a single-line comment — everything to end-of-line is skipped.
```

> Block comments (`/* … */`) may or may not be supported depending on implementation status. Single-line `//` comments are the primary form.

---

## Error Handling

When the tokenizer encounters a character that does not start any valid token, it:

1. Emits an `Unknown` token containing the offending character(s).
2. Records the exact `line`, `column` and `span/length`.
3. The compiler surfaces this as a lexer error and halts further analysis.

**Example error**

```
// source.bf — line 4
x = @value;
    ^
error: unknown token '@' at 4:5
```

## Requirements & Expectations

### Functional requirements

- **Complete coverage** — every valid ByteFrost lexeme must map to exactly one token type; no valid input must produce an `Unknown` token.
- **Precise location tracking** — `line` starts at `1`; `column` starts at `1`; both must be updated correctly across multi-line strings and escape sequences.
- **Keyword disambiguation** — identifiers that match the keyword table must be reclassified as `Keyword` before the token is emitted.
- **Greedy / maximal-munch matching** — the tokenizer must always consume the longest possible match (e.g. `<=` is one `Operator` token, not `<` followed by `=`).
- **Operator validity** — `&&`, `||`, `!`, and `^^` must **not** be tokenized as valid operators; they must produce `Unknown` (or an explicit lexer error).
- **Number base prefixes** — `0x…` (hex) and `0b…` (binary) must be recognized in addition to decimal integers.
- **Float formats** — leading-dot (`.5`) and trailing-dot (`2.`) floats must both be accepted.
- **Interpolated strings** — the raw string body including `{…}` fragments must be captured verbatim so the parser can process interpolation.
- **UTF-8 source** — character literals and string contents may contain any valid UTF-8 code point.
- **Single `EndOfFile`** — exactly one `EndOfFile` token must be emitted at the end of the stream.

### Performance expectations

- The tokenizer operates in a single forward pass — O(n) in the length of the source file.
- No backtracking; at most one character of lookahead is required for disambiguation.

### Interface contract

- Consumers receive a `Token` by value; the tokenizer retains no mutable shared state after the stream is produced.
- The token stream may be materialized eagerly (full vector) or consumed lazily (one token at a time via `nextToken()`).
- Calling `nextToken()` after `EndOfFile` is safe and must continue returning `EndOfFile` tokens without crashing.
